# Doctor Queue — implementation and verification status

The connected project remains the existing Next.js App Router / TypeScript application in GitHub repository `thewebcompany12/Doctor`, branch `main`, deployed through the Vercel project `doctor-queue`.

## Implemented

- Responsive landing page, public clinic directory and safe public clinic queue links/QR entry points.
- Email sign-in, forced first-login password change, password recovery request/callback/reset flow.
- Super Admin dashboard foundations: clinic search and lifecycle actions, plan/usage controls, recent administrative history, and authorized clinic/owner provisioning endpoint.
- Clinic workspace: profile/contact editing, branch creation, opening hours, staff invitation form, doctor/queue setup, walk-in token issue, call/recall, arrival, start/complete, skip/absent/cancel, pause/resume/close, queue history and staff appointment booking/status transitions.
- Supabase schema for clinics, memberships, doctors, branches, opening hours, queues, tokens, appointments, queue events, audit history, notifications and plan settings.
- Atomic/idempotent queue operations, clinic-wide daily token limits with clinic-row serialization, appointment slot uniqueness, composite tenant foreign keys, least-privilege table grants and private-schema security-definer implementations behind invoker RPC wrappers.
- Public queue status and clinic discovery are served from two read-only projection tables; neither exposes patient names, phone hashes, tracking secrets or appointment details.
- Patient experience: bilingual clinic search/filtering, public clinic detail and QR/share links, live queue pages with Realtime plus polling fallback, private token tracking links, estimated own-token position, cancellation while waiting, installable PWA shell, safe offline fallback, opt-in foreground alerts and a server-side Web Push worker. Online booking now validates clinic opening hours, plan limits, request idempotency, rate limits and private tracking-token storage.
- Version-matched source files for all 57 migrations applied to the connected Supabase project, including billing subscription, webhook-deny and foreign-key index migrations.

## Remaining blockers / limits

- `SUPABASE_SERVICE_ROLE_KEY` has a sensitive Vercel Production environment entry, but a secure metadata-only/decrypted check confirmed its stored value is empty. The Supabase integration exposes the publishable key but does not provide an authorized way to retrieve the service-role key; it cannot be invented or recovered from the publishable key. The project owner must copy the service-role secret from the correct Supabase project's API-key settings into Vercel as a sensitive server-only variable, then redeploy. Until then, privileged clinic provisioning, staff invitations, online booking and private tracking remain safely blocked and unverified. Never paste the secret into chat. Exact setup steps are in `docs/first-admin.md`.
- The connected Supabase project has no Auth users, no Super Admin role and no clinic rows (verified by live database counts). The first Super Admin must be provisioned through the documented operator-controlled procedure in `docs/first-admin.md`; this must not be automated without a verified identity.
- Add the production callback URL to Supabase Auth's redirect allow-list for password recovery.
- `vercel.json` schedules `/api/cron/push-reminders` daily at 09:00 UTC. Vercel reported that this project is on the Hobby plan, which rejects schedules more frequent than once per day; near-real-time reminders need a Pro plan or an authorized external scheduler. The worker remains safely disabled until the service-role key is configured. Do not expose the cron secret in GitHub or client code.
- Public online token issuance is implemented as a service-role-only RPC with hashed, expiring tracking secrets, per-key rate limiting, request idempotency and clinic-hours/plan gates. Online booking remains disabled by default and will fail safely until `SUPABASE_SERVICE_ROLE_KEY` is configured in Vercel.
- The production `NEXT_PUBLIC_VAPID_PUBLIC_KEY` has a non-empty public value and the latest READY deployment was built after that value was updated. The sensitive `VAPID_PRIVATE_KEY` and `CRON_SECRET` entries were inspected through the authorized decrypted environment endpoint and both values are empty. Background Web Push is therefore non-operational until the owner sets those secrets, redeploys, and verifies an authorized test subscription receives a real push-service acceptance. The Hobby-plan daily cadence is not suitable for timely turn alerts; upgrade the Vercel plan or configure a secure external scheduler for a five-minute cadence. Foreground browser alerts are opt-in and only work while the tracking page is open.
- CI has passed a synthetic 20-request concurrent token-allocation/idempotency test. Production-scale load testing and a full real-browser end-to-end run with real authorized test accounts remain outstanding.

Do not treat the platform as production-ready for real patient traffic until the owner has confirmed/configured the server-side service-role secret, provisioned a verified Super Admin, completed the Auth redirect allow-list setup, and run end-to-end workflows with authorized test accounts.
